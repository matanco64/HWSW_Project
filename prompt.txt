# FP64 datapath spike — grape_pipeline (sky130, Yosys+Verilator)

## Q1 — FPnew / CVFPU (openhwgroup/cvfpu)

**Ops/formats.** Yes on all counts: FP64 (binary64) add/sub, mul, FMA (4 flavours), div, sqrt, with all IEEE rounding modes incl. RNE ([README](https://github.com/openhwgroup/cvfpu)). Ops issue through one FMA-capable ADDMUL path; div/sqrt map to a DIVSQRT group.

**Div/sqrt units.** Three selectable via `DivSqrtSel` ([docs/README.md](https://github.com/openhwgroup/cvfpu/blob/develop/docs/README.md)): **PULP** (multi-format, FP64 incl.), **TH32** (T-Head OpenE906 — **FP32 only**, useless here), **THMULTI** (T-Head multi-format incl. FP64). The PULP unit is [pulp-platform/fpu_div_sqrt_mvp](https://github.com/pulp-platform/fpu_div_sqrt_mvp) (Solderpad v0.51): iterative, **non-pipelined**, 3 mantissa bits/cycle + 3 pre/post cycles → **FP64 div and sqrt = 21 cycles** ([FPnew paper, Table II](https://arxiv.org/abs/2007.01530)).

**Correct rounding — red flag.** The cvfpu README states: *"Some compliance issues with IEEE 754-2008 are currently known to exist for the PULP DivSqrt unit. Rounding mismatches… results being off by 1 ulp"*, and the inexact flag can be missed ([README](https://github.com/openhwgroup/cvfpu/blob/master/README.md)). This directly conflicts with our correctly-rounded-sqrt requirement. THMULTI's FP64 rounding status: *[unverified]*.

**Licence.** Solderpad HW License v0.51 (Apache-2.0-based, permissive); T-Head vendor code Apache-2.0 ([README](https://github.com/openhwgroup/cvfpu)).

**Verilator/Yosys.** Deliberately tool-friendly SystemVerilog: *"All array types are packed… SystemVerilog interfaces are not used due to poor support in some EDA tools"* ([docs](https://github.com/openhwgroup/cvfpu/blob/develop/docs/README.md)). Verilator: proven — CVA6 ships a Verilator testbench with FPnew ([cva6](https://github.com/openhwgroup/cva6)). Yosys: stock Yosys can't parse it ([cva6 #2319](https://github.com/openhwgroup/cva6/issues/2319)); it uses heavy packages/structs/enum arrays that trip some elaborators ([cvfpu #39](https://github.com/openhwgroup/cvfpu/issues/39)). **But it demonstrably goes through Yosys with the yosys-slang frontend**: Basilisk taped out RV64GC CVA6 (FP64 FPU included — 18.9 MFLOP/s/W on FP64 measured) end-to-end with Yosys-Slang in IHP 130 nm ([arXiv 2505.10060](https://arxiv.org/abs/2505.10060); earlier flow via SVase/sv2v, [arXiv 2406.15107](https://arxiv.org/abs/2406.15107)). So plan on `yosys-slang` (or sv2v) in the synth flow, not plain `read_verilog -sv`.

**Area/latency (GF22FDX silicon, [paper](https://arxiv.org/abs/2007.01530)).** Full transprecision FPU 247 kGE (FMA units 160 kGE across 5 formats, DIVSQRT 19 kGE); FP64 FMA latency 4 cycles, II=1, 923 MHz in 22 nm (expect ~10× lower Fmax in sky130 — Basilisk's whole 130 nm CVA6 ran 62–77 MHz).

## Implementation
